# 清单验证任务

本任务提供了根据清单验证文档的说明。代理应遵循这些说明以确保对文档进行彻底和系统的验证。

## 上下文

BMAD 方法使用各种清单来确保不同工件的质量和完整性。清单与其所需文档之间的映射在 `checklist-mappings` 中定义。这允许轻松添加新清单而无需修改此任务。

## 说明

1. **初始评估**

   - 检查 `checklist-mappings` 中可用的清单
   - 如果用户提供了清单名称：
     - 在 checklist-mappings.yml 中查找精确匹配
     - 如果没有精确匹配，尝试模糊匹配（例如，"architecture checklist" -> "architect-checklist"）
     - 如果找到多个匹配项，请用户澄清
     - 一旦匹配，使用映射中的 checklist_file 路径
   - 如果未指定清单：
     - 询问用户想使用哪个清单
     - 从 checklist-mappings.yml 中展示可用选项
   - 确认他们是否想要：
     - 逐节处理清单（交互模式）
     - 一次性处理（YOLO 模式）

2. **文档位置**

   - 在 `checklist-mappings` 中查找所需文档和默认位置
   - 对于每个所需文档：
     - 检查映射中指定的所有默认位置
     - 如果未找到，请用户提供文档位置
   - 验证所有所需文档是否可访问

3. **清单处理**

   如果处于交互模式：

   - 一次处理清单的每个部分
   - 对于每个部分：
     - 审查该部分的所有项目
     - 根据相关文档检查每个项目
     - 展示该部分的发现
     - 在继续下一部分之前获取用户确认

   如果处于 YOLO 模式：

   - 一次性处理所有部分
   - 创建所有发现的综合报告
   - 向用户展示完整分析

4. **验证方法**

   对于每个清单项目：

   - 阅读并理解要求
   - 在文档中寻找满足要求的证据
   - 考虑明确提及和隐含覆盖
   - 将项目标记为：
     - ✅ 通过：要求明确满足
     - ❌ 失败：要求未满足或覆盖不足
     - ⚠️ 部分：某些方面已覆盖但需要改进
     - N/A：不适用于此情况

5. **部分分析**

   对于每个部分：

   - 计算通过率
   - 识别失败项目中的共同主题
   - 提供具体的改进建议
   - 在交互模式下，与用户讨论发现
   - 记录任何用户决定或解释

6. **最终报告**

   准备包含以下内容的摘要：

   - 整体清单完成状态
   - 各部分的通过率
   - 失败项目列表及上下文
   - 具体的改进建议
   - 任何标记为 N/A 的部分或项目及其理由

## 特殊考虑

1. **架构清单**

   - 关注技术完整性和清晰度
   - 验证所有系统组件都已处理
   - 检查安全性和可扩展性考虑
   - 确保部署和运营方面已覆盖

2. **前端架构清单**

   - 验证 UI/UX 规范
   - 检查组件结构和组织
   - 验证状态管理方法
   - 确保响应式设计考虑

3. **产品经理清单**

   - 关注产品需求清晰度
   - 验证用户故事和验收标准
   - 检查市场和用户研究覆盖
   - 确保技术可行性已处理

4. **故事清单**
   - 验证清晰的验收标准
   - 检查技术上下文和依赖关系
   - 确保可测试性已处理
   - 验证用户价值明确说明

## 成功标准

清单验证在以下情况下完成：

1. 所有适用项目都已评估
2. 每个项目都有明确的通过/失败状态
3. 为失败项目提供具体建议
4. 用户已审查并确认发现
5. 最终报告记录了所有决定和理由

## 示例交互

代理："让我检查可用的清单...根据 checklist-mappings.yml，我们有几个选项。您想使用哪一个？"

用户："架构清单"

代理："您想逐节处理（交互式）还是立即获得完整分析（YOLO 模式）？"

用户："请用交互式"

代理："根据映射，我需要检查 architecture.md。默认位置是 docs/architecture.md。我应该在那里查找吗？"
